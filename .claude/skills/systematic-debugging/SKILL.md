# 系统化调试

## 概述

**核心原则：** 动手修复之前，必须先找到根因。只修症状就是失败。

**违反本流程的字面，就是违反调试的精神。**

## 铁律

```
未先完成根因调查，禁止任何修复
```

没走完阶段 1，就不准提出修复方案。

## 何时使用

任何技术问题都用：
- 测试失败
- 生产缺陷
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**以下情形尤其要用：**
- 时间压力大（紧急时刻最想瞎猜）
- "就一个小修复"显得显而易见
- 你已经试过好几个修复
- 上一个修复没生效
- 你没有完全理解这个问题

**这些时候也不许跳过：**
- 问题看着简单（简单缺陷也有根因）
- 你在赶时间（赶工保证返工）
- 老板要求"现在就修好"（系统化比乱撞快）

## 四个阶段

必须完成每个阶段，才能进入下一个。

### 阶段 1：根因调查

**尝试任何修复之前：**

1. **仔细读错误信息**
   - 不要跳过错误或警告
   - 它们常常直接包含解法
   - 完整读完栈回溯
   - 记下行号、文件路径、错误码

2. **稳定重现**
   - 能可靠触发吗？
   - 精确步骤是什么？
   - 每次都发生吗？
   - 无法重现 → 收集更多数据，不要猜

3. **检查最近的变更**
   - 什么变更可能导致这个问题？
   - git diff、最近的提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（安装入口 → 安装库 → 目标环境 → 校验器）：**

   **在提出修复之前，先加诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 核对环境/配置的传递
     - 检查每一层的状态

   跑一次，收集能显示"哪里断了"的证据
   然后分析证据，定位失效的组件
   然后专门调查那个组件
   ```

   **示例（本仓库安装器链路）：**
   ```bash
   # 第 1 层：便携安装器入口（shell→python，--dry-run 只打印计划不写入）
   bash scripts/install-ai-workflow.sh --target "$TARGET" --assistant claude --dry-run 2>&1 | tail -5

   # 第 2 层：安装库（python 模块能否加载）
   python3 -c "import sys; sys.path.insert(0,'scripts/lib'); import install_ai_workflow; print('安装库可导入')"

   # 第 3 层：目标环境（写权限）
   ls -ld "$TARGET/.ai" 2>/dev/null; test -w "$TARGET" && echo "目标可写"

   # 第 4 层：装后校验
   cd "$TARGET" && bash scripts/validate-workflow.sh --fast 2>&1 | tail -3
   ```

   **这能揭示：** 哪一层失败（入口计划打印 → ✓，安装库加载 → ✓，目标权限 → ✗）

5. **追踪数据流**

   **当错误深藏于调用栈时：**

   **速记版：**
   - 坏值从哪里产生？
   - 谁用坏值调用了这里？
   - 一路向上追，直到找到源头
   - 在源头修，不在症状修

### 阶段 2：模式分析

**修复之前先找模式：**

1. **找能正常工作的同类例子**
   - 在同一代码库里定位相似的、能正常工作的代码
   - 和坏掉的相比，哪些相似的东西是好的？

2. **对照参考实现**
   - 若在实现某个模式，把参考实现完整读完
   - 不要略读——逐行读
   - 完全理解模式后再套用

3. **列出差异**
   - 好的与坏之间有什么不同？
   - 列出每一个差异，再小也要列
   - 不要假设"这个不可能有影响"

4. **理解依赖**
   - 它还需要哪些别的组件？
   - 需要什么设置、配置、环境？
   - 它做了哪些假设？

### 阶段 3：假设与验证

**科学方法：**

1. **提出单一假设**
   - 清楚陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要含糊

2. **最小化验证**
   - 为验证假设做最小可能的改动
   - 一次只改一个变量
   - 不要一次修多个东西

3. **继续之前先确认**
   - 生效了？→ 阶段 4
   - 没生效？→ 提出新的假设
   - 不要在旧修复上继续叠修复

4. **不懂的时候**
   - 直说"我不理解 X"
   - 不要装懂
   - 求助
   - 再研究

### 阶段 4：实施

**修根因，不修症状：**

1. **先建失败测试用例**
   - 最简单的可能重现
   - 尽量做成自动化测试
   - 没有测试框架就写一次性测试脚本
   - 修复之前必须有
   - 写规范的失败测试时使用 `tdd` 技能（`.claude/skills/tdd/SKILL.md`）

2. **实施单一修复**
   - 只针对已定位的根因
   - 一次一个改动
   - 不做"顺手"的改进
   - 不捆绑重构

3. **验证修复**
   - 测试现在过了吗？
   - 没弄坏其他测试吗？
   - 问题真的解决了吗？
   - 声称成功之前先用 `verification` 技能（`.claude/skills/verification/SKILL.md`）

4. **修复没生效时**
   - 停
   - 数一数：已经试了几次修复？
   - 少于 3 次：带着新信息回到阶段 1 重新分析
   - **达到 3 次：停下，质疑架构（见下面第 5 条）**
   - 不经架构讨论，不许尝试第 4 次修复

5. **3 次以上修复失败：质疑架构**

   **架构有问题的信号：**
   - 每次修复都在不同位置暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能落地
   - 每次修复都在别处制造新症状

   **停下，质疑根本问题：**
   - 这个模式从根本上成立吗？
   - 我们是不是"纯靠惯性才硬撑着用它"？
   - 该重构架构，还是继续修症状？

   **再尝试更多修复之前，先与用户讨论**

   这不是"假设失败了"——这是架构选错了。

### 项目增补：坑位即时入库（ai-kb/memory）

**每个坑定位并解决后，立即**按 `.ai/memory/README.md` 定义的 memory 条目格式，追加到 `.ai/memory/<模块>.md`，条目标注来源变更。每个条目三行：标题行 `## YYYY-MM-DD · 来源变更 <变更名>`，随后 `**坑**：<现象>` 与 `**解**：<解法与注意事项>`。

禁止"归档时再补"——离开调试上下文后细节必然丢失。

## 红旗——停下，回到流程

发现自己在想这些时就亮了红灯：
- "先快速修一下，回头再查"
- "随便改个 X 试试看行不行"
- "多改几处，跑下测试"
- "跳过测试，我手工验一下"
- "八成是 X，直接修它"
- "我没完全懂，但这没准能行"
- "模式说的是 X，但我改着用"
- "主要问题是这些：[还没调查就列出修复方案]"
- 还没追踪数据流就提出解决方案
- **"再试一次修复"（已经失败 2 次以上时）**
- **每次修复都在不同位置暴露新问题**

**以上任何一条：停下。回到阶段 1。**

**3 次以上修复失败：** 质疑架构（见阶段 4 第 5 条）。

## 用户在示意你做错了

**留意这些纠偏信号：**
- "这不是没在发生吗？"——你假设了但没验证
- "它会给我们看……吗？"——你早该加证据收集
- "别猜了"——你在没理解的情况下提修复
- "深度推演这个"——质疑根本问题，不只是症状
- "我们卡住了？"（沮丧）——你的思路没在工作

**看到这些信号：停下。回到阶段 1。**

## 常见自我合理化

| 借口 | 现实 |
|--------|---------|
| "问题简单，不用走流程" | 简单问题也有根因。流程对简单缺陷来说很快。 |
| "紧急，没时间走流程" | 系统化调试比瞎猜乱试快。 |
| "先试这个，再调查" | 第一个修复定下基调。从一开始就做对。 |
| "等确认修复有效后再补测试" | 没测试的修复留不住。测试先行才能证明它。 |
| "一次修多处省时间" | 没法隔离哪处生效。还会引出新缺陷。 |
| "参考实现太长，我照猫画虎" | 一知半解保证出缺陷。完整读完它。 |
| "我看到问题了，直接修" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（已失败 2 次以上） | 3 次以上失败 = 架构问题。质疑模式，别再修了。 |

## 速查表

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. 根因** | 读错误、重现、查变更、收证据 | 理解"是什么"与"为什么" |
| **2. 模式** | 找正常例子、对照 | 列出差异 |
| **3. 假设** | 成型理论、最小验证 | 假设被确认，或换新假设 |
| **4. 实施** | 建测试、修复、验证 | 缺陷解决，测试通过 |

## 流程显示"没有根因"时

若系统调查表明问题确属环境性、时序性或外部性：

1. 你已经完成了流程
2. 记录你调查过什么
3. 实施恰当的应对（重试、超时、错误信息）
4. 加监控/日志供未来调查

**但是：** 95% 的"找不到根因"其实是调查不彻底。

## 辅助技术

以下技术属于系统化调试的一部分，核心规则已内联（根因回溯速记版见阶段 1）：

- **root-cause-tracing（根因回溯）**——沿调用栈向后追踪缺陷，找到最初的触发点
- **defense-in-depth（纵深防御）**——找到根因后，在多个层上加校验
- **condition-based-waiting（条件等待）**——用条件轮询取代随意定的超时
