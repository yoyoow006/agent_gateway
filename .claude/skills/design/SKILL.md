# Design——严格模式实现计划

Design 只属于严格模式。标准模式的 design/tasks 已在 Open 一次完成；遇到`模式: 标准`时不得创建 `openspec/plan`或索要第二次确认，直接等待唯一确认后进入 Build。

## 前置门禁

- proposal 必须是`模式: 严格`、`状态: 待确认规范`，且用户已明确确认四件套。
- 不满足时回到对应断点；计划未确认前不得写实现、配置或脚手架。

## 执行

1. 状态置为`设计中`。
2. 逐条对照 delta spec，补齐边界、错误处理和遗漏需求；若补充改变已确认范围，先请求重新确认。
3. 写 `openspec/plan/<变更名>.md`。
4. 自审规格覆盖、占位符和跨任务接口一致性。
5. 状态置为`待确认计划`，请求第二次实施前确认。

## 计划契约

计划必须让零上下文执行者能直接实施：

- 目标、架构、技术栈和逐字复制的全局约束。
- 按可独立测试、审查和回滚的职责单元分任务。
- 每任务列精确 Create/Modify/Test 路径、输入输出接口、实际测试或校验内容、运行命令和预期失败/成功结果。
- 运行时行为与缺陷修复写红—绿—重构；纯文档、知识或流程文本写内容契约、解析、格式和 diff 校验。
- 提交按可独立回滚的职责单元，不按每个 checklist 机械拆分。

禁止 TBD/TODO、“适当处理错误”、“与上个任务类似”或没有实际命令的“写测试”。

## 确认后：分支与 worktree 原子顺序

严格模式默认 worktree。由于已确认的四件套和计划可能尚未提交，顺序固定：

1. 记录当前基线分支；在当前工作区创建/切到 `feature/<变更名>`，只暂存本变更四件套、计划和状态。
2. 状态置为`构建中`，提交上述明确文件；不得带入用户其他未提交修改。
3. 需要隔离时先切回记录的基线分支，再用 git-worktrees 把**已存在且当前未检出**的 feature 分支挂到隔离目录；不得在 feature 已检出时执行 `git worktree add`。
4. 用户明确拒绝 worktree 时留在 feature 分支，并说明严格模式隔离风险；绝不在 main/master 实现。
5. 在最终实现工作区核对分支、状态和干净基线，交 Build 从首个未完成任务继续。

若用户修改导致无法安全切分支或提交明确文件，停止并请求决定，不复制、暂存或覆盖用户修改。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 标准模式也进入 Design | 直接回 Build；标准只有一次确认 |
| 用 tasks 标题代替严格计划 | 写到零上下文可执行的文件、接口和命令粒度 |
| 计划确认前建脚手架 | 脚手架也是实现，等待确认 |
| 先检出 feature 再直接 `worktree add` | 提交明确文件、切回基线，再挂载已存在分支 |
