# 编写技能

## 概述

**编写技能就是把测试驱动开发应用于流程文档。**

本仓库的技能存放在 `.claude/skills/<技能名>/SKILL.md`（仓库级技能是本仓库的唯一形态）。本技能改写自宿主 superpowers:writing-skills，其伴生参考未随仓库分发，核心规则已全部内联于本文。

你写测试用例（带子代理的施压场景），亲眼看它失败（基线行为），写技能（文档），亲眼看测试通过（代理遵从），重构（封堵漏洞）。

**核心原则：** 如果你没亲眼看过代理在没有技能时失败，你就不知道这个技能教的东西对不对。

**必备前置：** 使用本技能前必须理解本仓库的 tdd 技能——它定义根本的红—绿—重构循环；本文把 TDD 适配到文档。

**技能编辑的行为闭环：** 修改任一工作流技能正文后，Verify 终验必须重跑 `scripts/workflow-pressure-scenarios.md` 中与该技能行为相关的场景（相关性无法判定时重跑全部），逐场景记录 PASS/FAIL 于该变更的 OpenSpec 目录。

## 什么是技能

**技能是**经过验证的技术、模式或工具的参考指南，帮助未来的代理找到并应用有效方法。**技能不是**讲你某次如何解决一个问题的叙事。

## 技能的 TDD 映射

| TDD 概念 | 技能创建 |
|---|---|
| **测试用例** | 带子代理的施压场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（红）** | 无技能时代理违反规则（基线） |
| **测试通过（绿）** | 技能在场时代理遵从 |
| **重构** | 保持遵从的同时封堵漏洞 |

先写测试＝写技能前先跑基线场景；亲眼看它失败＝逐字记录代理使用的合理化借口；最小代码＝只写针对那些具体违规的技能；亲眼看它通过＝验证代理现在遵从；重构循环＝发现新合理化→封堵→复验。

## 何时创建技能

**创建，当：** 这项技术对你并非直觉显然、你会在多个项目中再次引用、模式适用面广、其他人会受益。

**不为以下创建：** 一次性解决方案；他处已有完善文档的标准实践；项目专属约定（放进 CLAUDE.md 等指令文件）；机械性约束——若可用正则/校验强制，就自动化它，文档留给需要判断力的场合。

## 技能类型

- **技术型**：有步骤可循的具体方法（基于条件的等待、根因追踪）
- **模式型**：思考问题的方式（带标志展平、测试不变量）
- **参考型**：API 文档、语法指南、工具文档

## 目录结构

```
.claude/skills/
  <技能名>/
    SKILL.md              # 主参考（必需）
    辅助文件.*            # 仅在需要时
```

**扁平命名空间**——全部技能处于同一个可搜索的命名空间。

**拆分独立文件，当：** 重型参考（100+ 行，如 API 文档、完整语法）或可复用工具（脚本、模板）。

**保持内联：** 原则与概念、代码模式（<50 行）、其余一切。

## SKILL.md 结构

frontmatter（YAML）两个必需字段 `name` 与 `description`，合计最多 1024 字符。`name` 只用字母、数字与连字符。`description` 第三人称、只描述何时使用（不描述它做什么），以"用于……时"开头，聚焦触发条件，尽量 ≤500 字符。

```markdown
---
name: skill-name-with-hyphens
description: 用于[具体触发条件与症状]时
---

# 技能名
## 概述        这是什么？一两句核心原则
## 何时使用    决策不显时的小型内联流程图；带症状条目；何时不用
## 核心模式    （技术/模式型）前后代码对比
## 速查        表格或条目，扫一眼可查
## 实现        简单模式内联；重型参考链接独立文件
## 常见错误    什么会出错＋修正
## 真实影响（可选）
```

## 技能发现优化（SDO）

**对发现至关重要：** 未来的代理靠读 description 决定某任务该加载哪些技能。让它能回答"我现在该读这个技能吗"。

### 1. description＝何时使用，不是技能做什么

以"用于……时"开头，含具体的触发器、症状与情境，**绝不概括技能的流程或工作流**。

**为何要紧：** 实测发现，当 description 概括了工作流，代理可能照着 description 行事而不读技能全文——一条写着"任务之间做代码审查"的 description 曾让代理只做了一次审查，尽管技能的流程图画着两次审查；把 description 改成纯触发条件后，代理正确读了流程图。概括工作流的 description 是一条代理会走的捷径，技能正文沦为被跳过的文档。

```yaml
# ❌ 坏：概括了工作流——代理照此行事而不读技能
description: 用于执行计划时——每任务派发子代理并在任务间做代码审查
# ✅ 好：只有触发条件
description: 用于在当前会话内执行含独立任务的实现计划时
```

内容要点：描述*问题*（竞态条件、行为不一致）而非*语言特定的症状*（setTimeout、sleep）；触发器保持技术无关，除非技能本身技术特定；用第三人称（会被注入系统提示）；为"即将违反规则"的症状补触发词。

### 2. 关键词覆盖

用代理会拿来搜的词：错误信息（"Hook timed out"、"ENOTEMPTY"、"race condition"）、症状（flaky、hanging、zombie、pollution）、同义词（timeout/hang/freeze、cleanup/teardown）、真实命令与库名。

### 3. 描述性命名

主动语态动词开头：`creating-skills` 而非 `skill-creation`；按你做什么或核心洞见命名：`condition-based-waiting` 优于 `async-test-helpers`。动名词（-ing）适合流程。

### 4. token 效率

技能正文按需载入会话，每个字符都是加载成本。目标（去空白字符数）：

- 常规技能：≤5000
- 方法论参考型技能（如本文）：≤7500

```bash
tr -d '[:space:]' < .claude/skills/<技能名>/SKILL.md | wc -m
```

手法：把细节移到工具 `--help`；用交叉引用代替重复其他技能已有的内容；压缩示例到最小可用；消灭冗余——同一模式不放多个示例、不解释命令本身能说明的东西。

### 5. 交叉引用其他技能

只用技能名，配显式的必需标记：

- ✅ `**必备前置：** 你必须理解 tdd`
- ❌ `见 .claude/skills/tdd/SKILL.md`（看不出是否必需）
- ❌ `@.claude/skills/tdd/SKILL.md`（@ 语法会立即强制加载文件，在还需要之前就烧掉上下文）

## 流程图使用

**只用于：** 不显眼的决策点、你可能停得太早的流程循环、"用 A 还是 B"的决策。

**绝不用：** 参考材料（→表格、列表）、代码示例（→markdown 代码块）、线性指令（→有序列表）；不用无语义标签（step1、helper2）。

## 代码示例

**一个出色的示例胜过多个平庸的。** 选最相关的语言（本仓库：测试与系统调试用 Shell/Python，数据处理用 Python）。好示例完整可运行、注释解释"为什么"、来自真实场景、拿来即可改编。不造填空式模板、不编假想示例、不用 5+ 种语言稀释——你擅长移植，一个好示例就够了。

## 文件组织

- **自包含技能**：全部内容内联于 SKILL.md（装得下且无重型参考需求时）。
- **带可复用工具**：SKILL.md（概述＋模式）＋可改编的辅助代码文件。
- **带重型参考**：SKILL.md（概述＋工作流）＋独立参考文件＋scripts/。参考材料大到无法内联才拆文件。

## 铁律（同 TDD）

```
没有先失败的测试，就没有技能
```

适用于新技能，也适用于对既有技能的**编辑**。先写技能再测试？删掉，从头再来。不测试就改技能？同样的违规。

**没有例外：** "简单的新增"不行；"只加一节"不行；"文档更新"不行；不许把未测试的改动留作"参考"；不许跑测试时"顺手改编"；删除就是删除。

**违反规则的字面，就是违反规则的精神。**

写完任何一个技能必须停下完成部署清单：不逐个测试就批量创建多个技能、当前技能未验证就进入下一个，都是对质量标准的违规。部署未测试的技能＝部署未测试的代码。

## 测试所有技能类型

| 类型 | 例 | 测什么 | 成功标准 |
|---|---|---|---|
| 纪律强制型 | tdd、verification | 理论题；施压场景（时间＋沉没成本＋疲劳多重叠加）；识别合理化借口并显式反制 | 最大压力下代理仍守规则 |
| 技术型 | 条件等待、根因追踪 | 应用场景；边界变体；缺信息测试 | 代理成功把技术应用于新场景 |
| 模式型 | 降复杂度、信息隐藏 | 识别何时适用；应用；反例 | 正确识别与运用心智模型 |
| 参考型 | API 文档、命令参考 | 检索场景；应用场景；缺口测试 | 找到并正确应用参考信息 |

## 跳过测试的常见自我合理化

| 借口 | 现实 |
|---|---|
| "技能显然够清楚" | 对你清楚 ≠ 对其他代理清楚。测它。 |
| "它只是参考" | 参考也会有缺口、有含糊小节。测检索。 |
| "出问题再测" | 问题＝代理用不了技能。部署前测。 |
| "学术审查就够了" | 读过 ≠ 用过。测应用场景。 |
| "没时间测" | 部署未测试的技能，日后修它更费时。15 分钟测试省数小时。 |

**以上每一条的意思都是：部署前测试。没有例外。**

## 形式匹配失败类型

写指引之前，先给基线失败分类。能让一种失败类型变得无懈可击的形式，放到另一种上会明显适得其反：

| 基线失败 | 正确形式 | 错误形式 |
|---|---|---|
| 压力下跳过/违反规则（知道该怎么做还是做了） | 禁令＋合理化表＋红旗（见"让技能对合理化免疫"） | 软指引（"prefer…"、"consider…"） |
| 遵从了，但产出形状不对（提示臃肿、裁决被埋） | 正向配方或契约：陈述产出*是*什么——组成部分、按什么顺序 | 禁令清单（"don't restate"、"never narrate"） |
| 在本来就会产出的东西里漏掉必需元素 | 结构化：模板里一个 REQUIRED 字段或槽位 | 模板旁的散文提醒 |
| 行为应随条件而变 | 键在可观察谓词上的条件句（"若简报存在，引用它"） | 无条件规则＋豁免条款 |

**为何禁令在塑形问题上适得其反：** 在竞争性激励（如"让提示自包含"）之下，代理会跟"不许 X"讨价还价。派发提示指引的措辞对比测试中，禁令组产出的有害内容明显多于配方组（分布完全分离），甚至比无指引对照组还差。配方没有讨价还价的空间：产出要么符合陈述的形状，要么不符合。自己的案例要微测，别想当然，但绝不默认伸手拿禁令。

**无论选哪种形式，都要守：**

- **不许有细微例外子句。**"除非要紧，否则不许 X"重新打开谈判——实测中给一个获胜配方附加细微例外子句会把它从稳定降级为噪声。真实的例外写成键在可观察谓词上的独立条件句。
- **豁免条款圈不住范围。**"此上限不适用于代码块"仍会压制代码块。若产出的一部分必须豁免，就重构结构，让规则够不着它。

## 让技能对合理化免疫

强制纪律的技能（如 tdd）需要抵御合理化——代理很聪明，压力之下会找漏洞。**适用范围：** 纪律型失败（知道规则却在压力下跳过）；对形状错误或漏元素的产出，基于禁令的免疫适得其反，改用上面的配方形式。

- **显式封堵每一个漏洞**：不只陈述规则——把具体的变通手法也禁掉。
- **处理"精神 vs 字面"之争**：尽早写明"违反规则的字面，就是违反规则的精神"，掐掉整类"我遵循的是精神"的合理化。
- **建合理化表**：从基线测试逐字捕获借口，每个借口配一条"现实"。
- **建红旗清单**：让代理合理化时容易自检——"以上任何一条出现：删掉重来"。
- **为违规症状更新 description**：向 description 加上"你即将违反规则"的症状触发词。

## 技能的红—绿—重构

### 红——写失败的测试（基线）

不带技能对子代理跑施压场景，逐字记录：他们做了什么选择、用了什么合理化借口、哪些压力触发了违规。写技能之前，你必须看到代理自然而然会做什么。

### 绿——写最小技能

写针对那些具体合理化的技能，不为假想情形添加多余内容；带技能重跑同一场景，代理现在应当遵从。

### 重构——封堵漏洞

代理找到了新的合理化？加显式反制，重测直到无懈可击。

### 全场景之前先微测措辞

完整的施压场景是最终关卡，但每次迭代又慢又贵；先用微测验证措辞本身：

1. **每次调用一个全新上下文样本**——裸 API 调用或单发子代理；系统提示＝该指引将来生活的真实上下文（完整技能，不是孤立指引），用户消息＝诱使失败的任务。
2. **永远带一个无指引对照组。** 对照组不表现出该失败，就没有要修的东西——停，别写指引。
3. **每个变体 5+ 次重复。** 单样本会说谎。
4. **逐条人工读每个命中。** 模板回声与被引用的反例会冒充命中，自动计数会同时高估失败与成功。
5. **方差本身就是指标。** 指引生效时重复收敛到同一形状；五次重复五种解读说明措辞没有约束力——先收紧形式，再加字数。

微测验证措辞；对纪律型技能，它不替代施压场景。

## 反模式

- ❌ **叙事式示例**（"某次会话里我们发现……"）——太特定，不可复用
- ❌ **多语言稀释**（example-js.js、example-py.py、example-go.go）——质量平庸，维护负担
- ❌ **流程图里放代码**——没法复制粘贴，难读
- ❌ **泛型标签**（helper1、step3、pattern4）——标签应当有语义

## 技能创建清单（TDD 版）

**重要：为下面每一条清单项建一条待办。**

**红阶段：**
- [ ] 创建施压场景（纪律型技能须 3+ 种叠加压力）
- [ ] 不带技能跑场景——逐字记录基线行为
- [ ] 识别合理化/失败中的模式

**绿阶段：**
- [ ] 名字只用字母、数字、连字符
- [ ] frontmatter 含 `name` 与 `description`（≤1024 字符），description 以"用于……时"开头、第三人称、无工作流概括
- [ ] 全文布关键词便于搜索（错误、症状、工具）
- [ ] 清晰的概述加核心原则
- [ ] 针对红阶段识别的具体基线失败
- [ ] 指引形式匹配失败类型（见"形式匹配失败类型"）
- [ ] 行为塑形类指引：措辞经无指引对照组微测（5+ 重复，逐条人工读命中）——纯参考型技能记 N/A
- [ ] 代码内联，或链接到独立文件
- [ ] 一个出色的示例（不求多语言）
- [ ] 带技能跑场景——验证代理现在遵从

**重构阶段：**
- [ ] 识别测试中出现的新合理化并加显式反制（纪律型）
- [ ] 用全部测试迭代建合理化表与红旗清单
- [ ] 重测直到无懈可击

**质量与部署：**
- [ ] 仅决策不显时用小型流程图；有速查表；有常见错误一节
- [ ] 无叙事式讲故事；辅助文件仅用于工具或重型参考
- [ ] token 效率达标（去空白字符数口径）
- [ ] 修改的是工作流技能时：Verify 终验重跑相关施压场景并记录
- [ ] 把技能提交进 git；（若广泛有用）考虑通过 PR 回馈

## 发现工作流

未来的代理如何找到你的技能：遇到问题 → 搜索技能（grep description）→ description 匹配 → 扫概述 → 读速查 → 只在实施时载入示例。**为此流程优化——可搜索的词放早、放多。**
