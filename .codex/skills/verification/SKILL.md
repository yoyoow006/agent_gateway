# 完成前验证

## 概述

**核心原则：** 证据先于断言，永远。

**违反这条规则的字面，就是违反这条规则的精神。**

## 铁律

```
没有新近的验证证据，禁止声称完成
```

本条消息里没有运行过验证命令，就不能声称它通过。

## 门禁函数

```
声称任何状态、或表达任何满意之前：

1. 识别：什么命令能证明这个声称？
2. 运行：执行完整命令（现跑、跑全）
3. 阅读：完整输出，查退出码，数失败数
4. 核对：输出是否支持这个声称？
   - 否：带着证据陈述实际状态
   - 是：带着证据陈述该声称
5. 然后才：做出声称

跳过任何一步 = 在撒谎，不是在验证
```

## 常见的失败情形

| 声称 | 必需的证据 | 不够格的证据 |
|-------|----------|----------------|
| 测试通过 | 测试命令输出：0 失败 | 上一次的运行、"应该会过" |
| Lint 干净 | Lint 输出：0 错误 | 部分检查、外推 |
| 构建成功 | 构建命令：退出码 0 | Lint 通过、日志看着不错 |
| 缺陷已修 | 测原始症状：通过 | 代码改了、假定修好了 |
| 回归测试有效 | 红-绿循环已验证 | 测试跑过一次通过 |
| 代理已完成 | VCS diff 显示有变更 | 代理汇报"成功" |
| 需求已满足 | 逐条清单核对 | 测试通过 |

## 红旗——停下

- 用"应该"、"大概"、"看起来"
- 验证之前就表达满意（"好了！"、"完美！"、"搞定！"等）
- 未验证就要提交/推送/建 PR
- 轻信子代理的成功汇报
- 依赖部分验证
- 想着"就这一次"
- 累了，想赶紧收工
- **任何没跑过验证就暗示成功的措辞**

## 合理化防线

| 借口 | 现实 |
|--------|---------|
| "现在应该能跑了" | 去跑验证命令 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Lint 过了" | Lint ≠ 编译器 |
| "代理说成功了" | 独立核实 |
| "我累了" | 疲惫不是借口 |
| "部分检查够了" | 部分证明不了任何东西 |
| "换个说法规则就不适用了" | 精神高于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] "全部测试通过"
❌ "现在应该过了" / "看着是对的"
```

**回归测试（TDD 红-绿）：**
```
✅ 编写 → 运行（通过）→ 还原修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了回归测试"（没做红-绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] "构建通过"
❌ "Lint 过了"（Lint 不检查编译）
```

**需求：**
```
✅ 重读计划 → 建清单 → 逐条核对 → 汇报缺口或完成
❌ "测试过了，本阶段完成"
```

**代理委派：**
```
✅ 代理汇报成功 → 查 VCS diff → 核实变更 → 汇报实际状态
❌ 轻信代理汇报
```

## 何时应用

**以下情形之前一律应用：**
- 任何形式的成功/完成声称
- 任何满意的表达
- 任何关于工作状态的正面陈述
- 提交、建 PR、宣告任务完成
- 进入下一个任务
- 向代理委派工作

**规则覆盖：**
- 一字不差的措辞
- 转述与同义词
- 暗示成功
- 任何传递完成/正确意味的沟通
