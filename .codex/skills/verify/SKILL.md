# Verify——按风险审查与终验

快速模式由 Open 路径完成针对性验证，不进入本技能。标准消除重复审查；严格保留独立关注面。

## 前置

- proposal 状态为`待验证`，tasks 全勾，Build 验证有输出证据。
- 主会话用 `.ai/tools/review_manifest.py freeze` 冻结所有受影响 Git 仓、comparison base 和工作区差异；reviewer 不得创建或刷新 manifest。
- 前置不满足则退回 Build，不用审查报告替代测试。

所有 reviewer 在读取范围前和形成结论前分别运行 `review_manifest.py verify`；任一次返回 `STALE` 立即停止，旧结论不得沿用。完整契约、finding 字段和 delta 复审见 `.ai/rules/review.md`。

## 标准：一次综合审查

对整个 diff 至多执行一次独立综合审查。小变更可由具备独立上下文的审查能力完成；不得再叠加任务级双审、全分支终审和规格/质量两个独立终审。

审查提示同时覆盖：

1. delta spec 每条 Requirement/Scenario 是否落地；
2. 正确性、错误路径、回归风险和测试有效性；
3. 安全、性能与可维护性；
4. 范围是否超出唯一确认。

Critical/Important 必须按共享台账处置。修复运行时行为继续用 TDD；主会话重冻后只复审 delta、直接消费者和继承的开放 finding，不执行第二次完整审查。

## 严格：双阶段独立审查

使用两个全新上下文审查者，顺序固定：

1. **规格符合性**：逐条核对 Requirements/Scenarios、禁止项和范围。
2. **代码质量**：在规格通过后审正确性、安全、性能、测试和可维护性。

审查者读取四件套、独立计划、有效 manifest、精确 diff 与测试摘要，不继承主会话结论。任务级审查不能替代这两阶段。每个独立关注面都在读取前与结论前 verify；任一阶段有 Critical/Important，修复并按 delta 范围复审；最多五轮后仍有争议则交用户裁决。

## 意见处理

逐条先复现或查证：

- 正确：按风险与 TDD 规则修复，重跑目标和回归验证。
- 错误：用代码、规格或命令证据说明，不做表演性修改。
- 已确认范围内的最小修复：沿用当前授权。
- 需要新增未确认行为、依赖、迁移或外部副作用：暂停、更新事实源并请求用户重新确认。

## 主会话终验

审查通过后，主会话亲自现跑：

- 变更相关测试与必要回归套件；
- 标准模式运行 `bash scripts/validate-workflow.sh --fast` 与变更相关目标/回归测试，逐项核对 `[PASS]`、`[FAIL]`、`[SKIP]` 和末尾汇总；变更触及工作流入口、技能、校验器或安装资产时改跑全量默认门禁，逐项核对同项汇总；
- 严格模式必须运行 `bash scripts/validate-workflow.sh --require-openspec`；OpenSpec 和仓库自带必需测试不得 SKIP，任一 FAIL 都阻断；
- `git diff --check`、目标 diff 和状态清单。

确认退出码、失败数、manifest 有效性、finding 状态、未验证范围和残余风险均符合门禁，再把状态置为`待归档`并提交审查修复/状态。`accepted-risk` 必须引用用户明确决定；审查者说“通过”不算终验证据。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 标准仍做任务审查＋整分支＋双终审 | 只保留一次全 diff 综合审查 |
| 严格把综合审查当双阶段 | 两个独立上下文、两个关注面 |
| 未验证就接受审查意见 | 先复现或核对规格 |
| 用旧测试输出声明完成 | 现跑并读取退出结果 |
