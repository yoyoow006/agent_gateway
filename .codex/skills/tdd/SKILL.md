# 测试驱动开发（TDD）

运行时行为先测试、看它按预期失败，再写最小实现。没有亲眼看到正确的红，就不知道测试能否抓住缺陷。

## 适用边界

| 变更 | 验证方式 |
|---|---|
| 新增/修改运行时行为、缺陷修复、行为代码重构 | 强制红—绿—重构 |
| 纯文档、注释、知识库、流程说明等不产生可执行行为的文本 | 不使用形式化 TDD；用内容契约、结构解析、示例、格式和 diff 校验 |
| 工作流技能本身 | 使用 writing-skills 的代理压力场景做红—绿 |
| 生成代码或一次性原型 | 只有用户明确同意例外时可跳过 |

文件后缀不是判断标准。修改配置语义、可执行示例或生成行为时，仍需对可观察运行时效果写测试。

## 铁律

```text
运行时实现代码 → 对应测试已存在，并先按预期失败过
否则           → 删除实现，从红阶段重来
```

不允许把先写的实现留作参考、边看边重写或事后补一个立即通过的测试。违反字面就是违反规则。

## 红—绿—重构

### 1. 红

- 一次只描述一个可观察行为，名字写清期望。
- 优先真实代码；只有无法控制的边界才 mock。
- 运行最小目标测试，确认是断言失败而非环境/语法错误，且失败原因正是行为缺失。
- 测试直接通过：它没有证明新行为，修正测试或重新确认需求。

### 2. 绿

- 只写让当前测试通过的最小实现，不顺手加功能或重构无关代码。
- 重跑目标测试，再跑受影响回归；输出必须无失败和意外警告。
- 失败时修实现；出现意外行为先用 systematic-debugging 找根因。

### 3. 重构

只在全绿后改善命名、重复和结构；不新增行为。每次重构后重跑测试。

## 测试质量

- 修改哪处生产代码会让测试失败？答不出说明测试不诚实。
- 断言结果和副作用，不断言 mock 被调用这种实现细节。
- 一个测试只测一个行为；测试准备巨大通常说明接口或耦合需要简化。
- 缺陷测试至少覆盖复现路径；边界和错误路径按风险补齐。

## 完成检查

- 每个运行时行为都有先红证据；
- 每次红的原因符合预期；
- 目标与相关回归全绿；
- 重构后仍全绿；
- 非运行时文本有与内容风险相称的解析、结构或 diff 证据。

## 常见合理化

| 借口 | 现实 |
|---|---|
| “太简单，事后补测试一样” | 立即通过的事后测试证明不了它能抓住缺陷 |
| “先留实现作参考” | 测试会被既有实现带偏；删除后从行为开始 |
| “Markdown 也必须制造红测” | 没有可执行行为时，用内容契约而不是仪式化失败 |
| “配置文件天然不用测” | 看它是否改变可观察运行时语义，不看后缀 |

出现代码先于测试、测试立即通过却继续、或“这次不一样”的合理化时，停止并从红阶段重来。
